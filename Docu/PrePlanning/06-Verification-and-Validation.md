# 6 Verification & Validation

[← Back to Index](Index.md)

Each test below has a unique ID so it can be cross-referenced against requirements in [07 Traceability Matrix](07-Traceability-Matrix.md). Tests fall into exactly two categories: **Unit Tests** (small scope) and **Integration Tests** (large scope). There is no separate "hardware"/"smoke"/"acceptance" split — those distinctions are captured instead by each Integration Test's **Scope** (Host/Target) and **Automation** columns.

## 6.1 Unit Tests (small scope)

Host-side, run under Ceedling/Unity, no target hardware required.

| ID | Name | Description |
|---|---|---|
| VT-UNIT-001 | Message Broker Publish/Subscribe | A message published into the broker input queue is delivered to every subscriber of its topic and to no subscriber of another topic (FR-103, FR-108, FR-110); a full subscriber output queue does not stall the broker, and a publisher can detect a full input queue via the backpressure API instead of blocking (NFR-105). |
| VT-UNIT-002 | Model Unit Tests | Model initialization and state-update accessor functions behave correctly. |
| VT-UNIT-003 | Control Statelessness | Calling a Control function twice with identical Model + input produces identical output both times (no hidden internal state). |
| VT-UNIT-004 | Maze & Movement Rules | Wall cells block movement (FR-010); pellet/power-pellet entry removes the item and increments the score (FR-011, FR-017); exiting a side tunnel wraps to the opposite opening on the same row (FR-012). |
| VT-UNIT-005 | Ghost & Frightened Logic | Each ghost's targeting is deterministic for its behavior (FR-014) and alternates between chase and scatter phases (FR-015); consuming a power pellet activates frightened mode, eating a frightened ghost scores a bonus and returns it to the pen without costing a life (FR-018, FR-019), and frightened mode ends after its duration (FR-020). |
| VT-UNIT-006 | Level & Difficulty Progression | The per-level difficulty parameters follow the defined monotonic progression (ghosts faster, frightened shorter, scatter less — FR-026); clearing a level advances the level and applies the next level's parameters and maze while carrying over score and lives (FR-021, FR-025), and clearing the final level completes the game (FR-027). |
| VT-UNIT-007 | Generated Maze Properties | Every property FR-029 lists, over 100 seeds each: the maze is left-right symmetric, framed by wall except where a tunnel crosses it, every walkable cell reachable from Pacman's start counting the tunnel wrap, the ghost house and gate at the coordinates the release and revival logic assume, four power pellets, a playable pellet count, and Pacman's start open and pellet-free. Plus: one seed always gives one maze, and neighbouring seeds give different ones. *(`test_maze_gen.c`. The port's faithfulness to the upstream generator is a separate check — the original and the port run under the same seeded PRNG and compared byte for byte over 300 seeds — which needs node and so lives in [M4 Random Mazes](../Design/M4-Random-Mazes.md) rather than in the unit suite.)* |
| VT-UNIT-008 | Derived Maze Appearance | The tile chosen for each cell, derived from where the walls are, reproduces the arcade's own hand-drawn tile map: 764 of 764 cells outside the two tunnel masses, with the 64 inside them excluded and asserted to be exactly 64. And on a *generated* maze, every wall cell bordering a corridor is given a drawing. *(`test_game_view.c`, FR-029 / DEC-030.)* |

## 6.2 Integration Tests (large scope)

Each on-target test is exposed as its own OTT CLI command (FR-106/FR-107, see [OTT CLI Framework](03-Architecture.md#37-on-target-test-ott-cli-framework)), modeled on the pattern used in [BareMetalHollowClockFw](https://github.com/MaxLell/BareMetalHollowClockFw). **Automation** values:
- **Automatic** — triggerable and verifiable by the external Python test harness with no human involved.
- **Manual, button-confirmed** — the firmware displays/logs the expected result and waits for the user to press the Nucleo user button to confirm; the test fails if the button isn't pressed within a timeout. This replaces plain "look at the screen" inspection with a pass/fail signal the firmware can still report.

A third category, *manual one-time bring-up* — a continuity check with a multimeter, done once and not repeatable via the CLI — was defined here and is deliberately gone. Board Bring-Up settled the pin map without it, by writing tests that make the hardware answer: a display that returns its identification registers proves five pins at once, and a key whose *name* the operator recognises proves the mapping in a way a beeping multimeter cannot. A check that leaves no repeatable artefact is worth avoiding where a test can take its place.

**A note on what a confirmation is worth.** A "Manual, button-confirmed" test must state what the operator should *see*, not what the firmware drew. Bring-up produced a case where every colour was displayed as its complement and the confirmation passed anyway, because "eight colour bars" in reversed order still looks like eight colour bars. The tests below therefore name the expected outcome ("the whole screen must be RED, not cyan").

| ID | Name | Scope | Automation | Description |
|---|---|---|---|---|
| VT-INT-001 | Power-On & Enumeration | Host tool + Target | Automatic | The Nucleo board powers on and the STLINK V3 enumerates as a debug + virtual COM port device over USB. |
| VT-INT-002 | Serial Console Output | Target | Automatic | The STLINK V3 virtual COM port produces a known, readable boot banner from the target. |
| VT-INT-006 | Display Output | Target | Manual, button-confirmed | `ott display_test` fills the panel with red, green and blue, draws the eight colour bars and a border with a marked origin, then a yellow disc through the full `framebuffer` -> `gfx` -> `display` path. Each screen is announced by **what it must look like**, so a wrong pixel format, byte order or inversion fails rather than merely looking odd. The operator confirms with the USER button. *(As built — the panel is an ST7789V; see [M2 Board Bring-Up §1.6](../Design/M2-Board-Bring-Up.md).)* |
| VT-INT-008 | Host Build Launch | Host | Automatic | The host-built Pacman binary launches, opens an SDL window, and renders at least one frame. |
| VT-INT-010 | Game Logic Playthrough (E2E) | Host | Automatic | A scripted sequence of directional inputs is fed through the pub-sub bus into Control; the resulting Model state — Pacman position, pellet/power-pellet consumption, score, ghost positions, and frightened mode — matches the expected outcome after each move. |
| VT-INT-011 | Boot Sequence | Target | Automatic | `run_ott.py --suite` resets the board and watches the shell announce the two screens as it reaches them: `loading screen` then `menu screen`, both inside NFR-001. The screens themselves are pixels and only an operator can judge those (VT-INT-020 covers whether the panel and the coordinate system agree at all); the *order* and the *timing* are what the firmware says over the serial line as it goes, and that is what makes this one automatic. |
| VT-INT-012 | Game Start via Button | Target | Manual, button-confirmed (flow: Automatic) | The operator presses the Nucleo button or the stick's centre key at the menu and the `game screen` line confirms the run started. The *flow* needs no operator: the `start` console command presses the same key, so menu → game → score → menu can be walked from the harness as often as you like — which is how it was confirmed that several runs in a row leave the board standing. What only a finger can confirm is that the key on the board is wired to it. |
| VT-INT-013 | Directional Movement | Target | Manual, button-confirmed (latency: Automatic) | The user is prompted to push each joystick direction (FR-004) in turn and confirm that Pacman moves that way; input-to-render latency (NFR-003) is measured automatically from serial-logged input/render timestamps. |
| VT-INT-014 | Game Over (Lives Exhausted) | Host | Automatic | A scripted input sequence causes Pacman to be caught repeatedly; each non-final catch decrements lives and respawns Pacman/ghosts to continue the level (FR-024); after the last life the game ends, the final score is shown (score screen, FR-023), and the Model returns to the menu state. |
| VT-INT-015 | High Score Update & Persistence | Target | Automatic | `ott high_score` erases the reserved flash page, confirms it reads back empty, writes three known scores through the ordinary `high_score` path, re-reads them from flash and compares — then puts the table back the way it found it. It also reports what an erase and three writes cost, which is the number behind offering a run to the table only when it ends. What the mocked unit tests cannot reach is exactly this: that the page the linker reserved is the page the driver erases, that a 128-bit program takes, and that the instruction cache is not answering with what the page used to hold. |
| VT-INT-016 | Rendering Smoothness | Target | Automatic | The harness parses serial-logged frame-render timestamps captured during a scripted gameplay run and confirms the achieved rate meets NFR-002. |
| VT-INT-017 | Level Progression & Completion (E2E) | Host | Automatic | A scripted run clears the maze level after level: clearing a non-final level restores the pellets and applies the next level's difficulty while carrying score and lives (FR-021, FR-025, FR-026); no level is easier than the one before it; clearing the 21st completes the game as won (FR-027), shows the score screen (FR-023), and returns to the menu. |
| VT-INT-018 | Display Identity & Pin Map | Target | Automatic | `ott display_id` resets the controller and reads its identification registers at **both** chip-select polarities, confirming an ST7789V answers. An answer proves SCK, MOSI, MISO, CS and DCX at once — a wrong one of them produces no reply — so this closes the display half of the pin map without a multimeter. |
| VT-INT-019 | Joystick Key Mapping | Target | Manual, button-confirmed | `ott joystick` prints the **name** of each key as it is pressed and passes once all five have been seen. The operator checks that the name matches the key pushed — a test that merely counted presses would also pass with two directions swapped. Closes the input half of the pin map. |
| VT-INT-020 | Input & Display Integration | Target | Manual, button-confirmed (cost: Automatic) | `ott joystick_dot` moves a dot one cell per key press using partial updates only. This is the first test in which input and display must agree: a swapped axis or an inverted row order passes VT-INT-006 and VT-INT-019 separately and fails here. The drawing half of NFR-003 is timed automatically over 100 moves. |
| VT-INT-021 | Motion Smoothness | Target | Manual, button-confirmed (rate: Automatic) | `ott animation` runs five actors at a constant speed while varying only the frame rate, so the step per frame changes and the speed does not — which is what makes stutter visible. Each pass must hold the rate it asked for, checked automatically; the operator judges where motion stops looking smooth and can steer the rate with the joystick. This is what NFR-002's figure was chosen against, as distinct from VT-INT-016, which confirms the real game keeps it. |
| VT-INT-022 | The Game on the Board (E2E) | Target | Manual, button-confirmed (frame cost: Automatic) | `ott pacman` starts a run immediately — no menu, no start screen — and hands over the joystick. It is the only test in which the rules, the view, the panel, the stick and the frame budget are all real at once: the host application (VT-INT-010/014/017) runs the same `game_session` frame in a window, which is evidence about the game and none about this hardware. The operator judges the maze, the turning, the ghosts leaving the house, a power pellet and a level turning over; the cost of a frame is measured automatically over 300 frames and reported against the NFR-002 budget, which is VT-INT-016 taken on the real game rather than on `animation`'s actors. |

## 6.3 Test Harness (Python)

`Firmware/Test/run_ott.py` drives every **Automatic** test above sequentially over the serial console (sending the OTT command, reading back PASS/FAIL) and reports a summary. **Manual, button-confirmed** tests are excluded from that run list — they have the same OTT command but are streamed live, with a long timeout, because they need a human in the loop.

One operational note, learned the hard way: the harness reads the ST-LINK's virtual COM port, and **a second reader on the same port makes a run look like failing hardware**. Two readers split the incoming bytes, so the output arrives with characters missing and the test times out or reports nonsense. `run_ott.py` therefore checks at start-up whether another process holds the port and names it.
