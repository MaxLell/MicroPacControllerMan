# 11 Decisions & As-Built

[← Back to Index](Index.md)

This document records **implementation decisions actually taken** and where the
built firmware **deviates from the intended design** described elsewhere in this
set. It exists so a reader starting from zero can tell what is true *today* (as
built) from what is *planned*. Requirements ([02](02-Requirements.md)) state the
target; this log states the current reality and the reasoning.

Decisions carry a `DEC-xxx` ID. When a decision is superseded, mark it and add a
new row rather than editing history.

| DEC-012 | **Pivot back to STM32CubeMX + STM32 HAL** for the M2 board bring-up (supersedes DEC-001/DEC-009). | DEC-013 | **Post-M2 structural refactor from the owner's review** (PR #6; partially supersedes DEC-009's naming). Five things changed. (1) **BSP naming unified on the `_bsp` suffix** — `bsp_i2c`→`i2c_bsp`, `bsp_spi`→`spi_bsp`, `uart`→`uart_bsp`, `systick`→`systick_bsp` — which also retires the DEC-012 extern-handle workaround, since the modules no longer clash with CubeMX's generated `i2c.h`/`spi.h` and include them directly. (2) **New `Bsp/dio_bsp`**, modelled on the reference project's `dio_bsp` (`set_pin`/`get_pin`, plus `toggle_pin` for the display's EXTCOMIN): pins are named through `dio_bsp_pin_e` and it is the **only** module permitted to call HAL GPIO. (3) **`Bsp/button` replaced by `Bsp/switch` + `Bsp/user_button`** — a reusable debounced-input primitive and this board's B1/PC13 instance — sampled at a steady 1 ms from a tick hook rather than at main-loop speed. (4) **`millis()`/`delay_ms()` removed from the tick module** in favour of `Services/delay` (the one blocking wait) and `Services/sw_timer` (all timeouts and periodic work, ported from the reference project); no tick arithmetic remains in the firmware. (5) **`retain_ram` reduced to the reference API** (`retained_ram_write`/`read` over a byte buffer) with the `ott_spec` layout moved into `Test/Target/ott.c`, so the memory module no longer knows the data format. Alongside these, the [c-code-style](https://github.com/MaxLell/c-code-style) standard was applied across every file (Allman braces, `in_`/`out_` pointer prefixes, named constants, no abbreviations, `ASSERT` preconditions) with the config vendored as `Firmware/.clang-format`; the `lacheck`/`dispdiag` diagnostics were deleted now that R-001 is closed; and the cross-toolchain moved into `CMakeLists.txt` above `project()`, removing `Firmware/cmake/`. | post-M2 | Convergence with the reference firmware so modules are recognisable across both repos, and one owner per hardware-access path (GPIO, timing) instead of several. | Layout rules updated in [§3.9](03-Architecture.md#39-firmware-source-tree-layout). The 1 ms hook is a strong override of the HAL's `__weak HAL_IncTick()`, chosen so the generated `stm32g4xx_it.c` needs no edit and a CubeMX regen cannot drop it. The `button` OTT became `user_button`. |

| DEC-014 | **Message broker built as specified in [§3.2](03-Architecture.md#32-message-broker).** Instance-based (`self` first, all state inside), subscribers register an **output queue** rather than a callback, fixed-size messages copied by value, per-subscriber drop counters for slow-consumer isolation, and a `has_input_space` backpressure check (NFR-105). Split into four modules: `Services/msg` (the vocabulary of [§3.3](03-Architecture.md#33-message-definitions), header-only), `Services/circular_buffer` (a generic element-agnostic ring buffer, caller-supplied storage, no heap), `Services/msg_queue` (a `msg_t`-typed skin over it) and `Services/msg_broker`. Names follow §3.2.1's sketch — `msg_*`, `msg_t`, `msg_id_e` — and the topic IDs match §3.3's table verbatim (`MSG_INPUT_DIRECTION`, ...). | M3 | Everything communicates through the broker (FR-103), so its types appear in every module. `msg` is the one abbreviation the owner explicitly wants kept short (PR #8 review), which narrows the no-abbreviation rule of review note 1.1.2 rather than replacing it. The ring buffer is separate because the arithmetic is identical whatever is queued and is where wrap-around bugs live. | FR-108 wants a worker task per broker; FreeRTOS is M4, so `msg_broker_process()` is the worker body called from the super-loop, with no API change when the task arrives. **(Threading superseded by DEC-027: there is no task, and the owning loop names its own fan-out point.)** Unlike the singleton it was adapted from, `msg_broker_init()` does **not** assert "not already initialized" — on an instance that reads uninitialized memory. 102 host unit tests; not yet wired into `app_main`, so it enters the binary with the first module that uses it. |
| DEC-015 | **Active-Object base built as the reusable template of [§3.5](03-Architecture.md#35-software-module-template-active-object)** (FR-109), in `Services/active_object`. An object owns its **single inbound queue** (a `msg_subscriber_t`), a dispatch handler, and an opaque `context` pointer to the module's private state — so a module contributes only its handler and its data, and the state is reachable only while that handler runs. Subscribing takes the broker explicitly, because a module may sit on the system broker or on the game's internal one (FR-110, §3.6). Two of the pattern's rules are **enforced rather than documented**: run-to-completion asserts on re-entry (a handler that dispatches back into its own object is caught instead of mutating state mid-update), and asynchronous-only follows from the broker's output queue, which a unit test pins down by showing a handler's publish is not delivered until the broker runs again. | M3 | §3.5 asks for the boilerplate to be factored out; §3.6 alone puts seven more modules on this base, so its invariants are worth checking once here rather than per module. | Polling `active_object_process_all()` is the **host** model, not a stand-in for tasks: §3.4 says the host build runs these "as plain functions/loops driven by the SDL event loop instead of tasks". Under FreeRTOS (M4, DEC-002) the task body becomes the same call in a loop and no module changes. **(Superseded by DEC-027: no RTOS arrives, and `score` is the one module on the template rather than every module.)** **No FSM helper yet** — §3.5 mentions a state machine, but the reference project keeps `fsm` as a separate module; it gets added when a module actually needs states. 115 host unit tests. |

| DEC-016 | **No message carries a pointer; the render path is three modules and two messages.** The [R-007](05-Risks-Assumptions-and-Dependencies.md#51-risks) exception — a handle to a double-buffered snapshot — is withdrawn. **Game** publishes `MSG_GAME_STATE`, one coherent state per simulation step (56 bytes: two 99-bit pellet maps, five actors with their between-cell progress, and a few counters). **Game-View** holds it, runs at the *frame* rate rather than the step rate, interpolates ([10 §10.1](10-Pacman-Game-Design.md)) and publishes `MSG_DISPLAY_LIST` — what should be on screen now, in pixels. **Render** draws it and is the only module that decides **what changed**. Also settled: entities keep cell-granular *rules* and gain a sub-cell fraction that only the view reads. | M3 | R-007's premise was wrong. What is large is the rendered image, not the state, and the image never has to travel. Withdrawing the exception removes the second frame buffer with it — which was the harder problem, since one is 60 % of SRAM and two do not fit. Interpolation is what makes the 60 FPS of NFR-002 worth having: cell-granular drawing is a 21-pixel jump 6.7 times a second, which [M2 §3.2](../Design/M2-Board-Bring-Up.md) measured as visibly choppy no matter what the panel does. | Render owns the delta because it is the only module that knows what it drew *and* what it costs — 2.08 ms for two small rectangles against 252 ms for a full frame. `MSG_PAYLOAD_MAX_SIZE` grows from 16 to 64 bytes and `msg.h` stops including `framebuffer.h`, so the message vocabulary no longer depends on the image format at all. |
| DEC-017 | **One maze for every level; the difficulty is the arcade's own, in a module of its own.** FR-025's five distinct mazes are withdrawn. The playfield is a single 28 × 31 layout ([10 §10.2](10-Pacman-Game-Design.md)) — the size FR-022 always asked for, and only now affordable, since 28 columns of 8 px need a panel wider than the 128 px this project started on. What makes level 15 harder than level 1 is instead the progression of [§10.9](10-Pacman-Game-Design.md), transcribed from the arcade: per-level speeds for Pacman and the ghosts, a ghost that crawls in the tunnel, a Pacman who is slower while chewing, a shrinking frightened window with a flashing warning, per-level scatter/chase plans, and **Cruise Elroy** — Blinky accelerating in two stages as the maze empties, and no longer going home during scatter. It lives in `App/difficulty`, a stateless lookup holding the table in the arcade's own units (percentages of full speed, dot counts, seconds) and handing out milliseconds. FR-027's finish line moves from level 5 to **level 21**. | M3 | Five hand-authored mazes were a way of making levels differ, invented because the difficulty model was thin. The arcade's answer is better and is already designed: it is the difference between "the walls moved" and "Blinky is behind you and there are nine pellets left". Keeping the table in percentages is what lets the transcription be reviewed line by line against its source, which for twenty-one rows of hand-typed numbers is the only real defence. 21 is where the arcade's table stops changing, so it is the honest place to end a run. | Each ghost needs its own movement accumulator, since Elroy and the tunnel mean no two of them share a speed. The Elroy thresholds are absolute pellet counts and transfer unmodified only because this maze holds 243 pellets against the arcade's 244; `playfield_get_total_pellet_count()` and a unit test exist so a redraw cannot break that quietly. Tunnel cells are marked in the map rather than derived from the tunnel's row — the junction the tunnel opens onto is not tunnel. `MSG_PAYLOAD_MAX_SIZE` grows to 256 bytes, because the state's two pellet maps are now 868 bits each; the argument that withdrew [R-007](05-Risks-Assumptions-and-Dependencies.md#51-risks) still holds, with three orders of magnitude of margin instead of four. `playfield_load_level(pf, level)` becomes `playfield_load(pf)`. |

| DEC-018 | **Interpolation measures the step already taken, and the sprites are the arcade's own.** Two fixes that both came out of playing it. (1) `cell_progress_t` changes meaning from "how far towards the next cell" to **"how far into this cell from the last one"**, and Game-View draws backwards from the cell instead of forwards along the facing. An entity that did not move reports *arrived* rather than a fraction. (2) The hand-drawn art in `sprite_set` is replaced by the **1980 sprite and tile ROM**, decoded offline: Pacman's three-frame chew per direction, the ghosts' two-frame skirt per direction, the frightened pair, and the two pellet tiles. West and north Pacman are the cabinet's hardware mirrors of east and south, with its position offset folded into the data and a unit test checking the mirrors against their originals. | M3 | (1) was a real bug with a clear cause: the old scheme interpolated towards a cell that is only chosen when the next step happens, so at a corner it either slid a cell the wrong way and snapped, or — facing a wall — stood still for a period and then jumped. Both are the same mistake, extrapolating along a guess. Measuring the step that has already happened needs no guess. (2) the hand-drawn figures were placeholders and looked it; the originals are a fixed, checkable reference and cost nothing at run time. | The frame at a step boundary is now identical either side of a turn, which is what a unit test asserts rather than an eye. A dot is eaten the moment the model enters the cell, so it now vanishes as Pacman's leading edge reaches it rather than as his centre does — half a sprite earlier than the arcade, and the price of not guessing. Pacman's chew and the ghosts' skirt are clocked by the step rather than by a frame counter, so a ghost slowed by the tunnel visibly waves more slowly. The sprite data is Namco's: fine for a private build, not for anything distributed. |

| DEC-019 | **The maze is transcribed, not authored, and it is written down twice.** The walls are drawn with the arcade's own line and corner tiles — thin blue outlines and a pink gate instead of filled blocks — which forced the layout itself: a tile map only fits the maze it was drawn for, and the hand-drawn 28 × 31 one was wrong in 94 of its 868 cells. Both now come from the same source. `playfield` keeps the **rules** map (wall, pellet, pen, tunnel) and `game_view` keeps the **appearance** map, one arcade tile letter per cell, with `sprite_set` holding what each letter draws. `game_view_is_wall_drawn_at()` exists so a unit test can check every cell of the two against each other. | M3 | Filled blocks were the last thing that still looked hand-made. Deriving the tiles from the wall bitmap instead would have meant inventing corner art — the very thing the owner had just rejected for the sprites. Keeping the two maps apart is the MVC split doing its job: neither is derivable from the other, so one table cannot serve both, and a mechanical check is what makes the duplication safe rather than a trap. | The pellet count becomes **exactly the arcade's 244**, so §10.9's Cruise Elroy thresholds stop depending on the coincidence that the hand-drawn maze held 243. Pacman now starts in the corridor below the ghost house, walled above and below, and the house is three rows rather than two — both of which moved a good deal of test scaffolding. `game_view_t` loses its 5 kB `playfield` copy, which only the old wall lookup needed. The gate is drawn but passable: the arcade's one-way rule keeping Pacman out of the house is still not modelled. |

| DEC-020 | **The HUD is a fixed list of slots, and Render sends a tile as a tile.** The score, level and lives ([10 §10.10](10-Pacman-Game-Design.md)) are described as a fixed-length list whose content is a pure function of the state; asking the same question of the state last drawn gives what is on the panel, and only the difference is sent. `game_view_t` keeps a 20-byte `drawn_hud` for that. The alphabet is the arcade's own font, decoded from the tile ROM at its ASCII codes, so `sprite_set_get_glyph()` is arithmetic. Separately, `render_draw` was presenting **every** background item as `RENDER_SPRITE_MAX_SIZE` — 16 x 16 for an 8 x 8 tile — and now uses the sprite's own size. | M3 | The score moves on almost every pellet, so "redraw the HUD when something changed" had to mean the digit that moved rather than all seven; at 5 Mbit/s the difference is bigger than the five actors cost. The transfer bug was found by measuring the target footprint rather than by looking: it quadrupled every field transfer, which is invisible on a frame that changes one pellet and is a third of a second of black screen across the 868 tiles of a level change. | The level repaint drops from roughly 0.36 s to 0.1 s, and a test now asserts what size actually reaches the display port rather than only what lands in the frame buffer. Lives are drawn as the count the model holds, not the arcade's reserve men, so the panel cannot disagree with `game_get_lives()`. The whole A-Z is in flash for two words — 2 kB, and the menu and score screens (FR-001/002/023) are all text. Cost measured with arm-none-eabi-gcc: +2.5 kB flash, +20 B RAM. |

| DEC-021 | **One frame buffer, owned by Render, borrowed by the on-target tests.** `Test/Target/ott_framebuffer` and `App/render` had each allocated a 153,600-byte buffer, both headers stating that only one fits. `ott_framebuffer_get()` now forwards to `render_get_framebuffer()`, which is writable for the purpose, and `App/render` (with `sprite_set` and `Services/sprite`) joins the target build. The tests keep drawing with `gfx` and presenting with `display` — they do **not** draw through Render. | M4 prep | 153,600 bytes is 60 % of the contiguous SRAM; two of them are 300 kB against 256 kB and would not link. Nothing had noticed because the game is not in the target image yet, so this was the first thing standing in the way of wiring it. Routing the tests *through* Render was considered and rejected: `render_draw` takes a display list of sprites and these draw primitives, and `ott_display_test` measures `display_present` against `display_present_region` — which is precisely the decision Render takes over, so putting it in the path would remove the thing being measured. A bring-up test also has to fail in one place, and through Render a red result could be the driver, Render or `sprite_set`. | The dependency now runs `Test/Target` → `App/`, the wrong way for a test of a lower layer. Accepted knowingly: the alternative was a third module owning the buffer, and one forwarding call was the smaller price. `--gc-sections` keeps the cost at 8 bytes of flash, because only the accessor is reachable until the game itself is wired. A caller drawing straight into the buffer steps around save-under, which is harmless only because the OTT flow runs one scenario per reset ([09](09-OTT-Mechanism-and-Reset-Flow.md)) and the game is not running during it. |

| DEC-022 | **The game is normal operation; a test replaces it for one boot.** `app_main` starts the game at power-on and runs it in a loop that also polls the console. `ott <name>` still stores the request and resets, and `ott_execute_pending()` now returns whether it ran — on that boot the board stays on the console rather than starting the game, and `reset` brings the game back. Joystick directions are read as a *level* once per frame; the centre key starts the next run once one has ended. `App/render` was already in the target build (DEC-021) and the rest of the game joins it. | M3 | The owner asked for exactly this shape: the game starts regularly, the console stays available, and configuring a test reboots into it and interrupts the game. Scheduling already worked that way — what was missing was that the game and a test are *alternatives* for a boot, not a sequence: starting the game after a test would paint over the panel the test left behind, while the harness is still reading the verdict off the same line. | Wiring the game in broke `run_ott.py`, and the failure was worth the trouble of chasing: the UART receive register holds one character with no FIFO, and a loop that now spends milliseconds inside a frame drops most of a command line. `console_poll_receive()` samples it from the 1 ms tick into a ring buffer of the console's own — hand-rolled rather than `Services/circular_buffer`, because that one shares a `count` between producer and consumer and here the producer is an interrupt. Characters must still arrive more than a millisecond apart, which typing and the harness satisfy and pasting does not ([RF-016](../Refactoring-Backlog.md)). Measured on the board: RAM 169,968 B (64.8 %), flash 80,857 B (15.4 %). Verified on hardware: game runs, console answers 25 of 25 command lines during play, OTT suite green three runs in a row. |

| DEC-023 | **The ghosts, checked line by line against the Pac-Man Dossier.** Distance becomes the squared straight line rather than Manhattan; Pinky looks 4 cells ahead rather than 2, Inky's offset is 2 rather than 1, Clyde breaks off at 8 rather than 4. Forced reversals happen on chase↔scatter and on entering frightened, but no longer on leaving it. **(Superseded by [DEC-037]: forced reversals are gone entirely.)** The ghost house and its gate are their own cell kinds: Pacman may never cross the gate and a ghost only on its way out or after being eaten. Ghosts start where the arcade puts them — Blinky outside, above the gate — and are released by the arcade's dot counters, global counter and idle timer. The scatter targets move to the unreachable dead space above and below the maze, and are re-assigned: **Blinky top-right, Pinky top-left, Inky bottom-right, Clyde bottom-left**. Seeking becomes a route search. | M3 | The owner asked for A\* and for a comparison against the Dossier; the comparison turned out to explain more than the request did. "The ghosts feel dim" was arithmetic, not intelligence: Manhattan distance makes a detour cost the same as going straight, so visibly worse directions reached the tie-break as equals and won on ordering alone. The house being an ordinary corridor is why they wandered back into their cage and why Pacman could follow. The scatter corners were swapped within each pair, sending all four to the opposite side of the maze. | The route search is breadth-first rather than heuristic, and that is a considered choice: Pinky and Inky aim at cells that usually cannot be reached at all, and no heuristic prunes a search for something that is not there. Where the target is reachable it returns A\*'s route; where it is not, the nearest reachable cell — which A\* has no answer for. Fleeing stays greedy. Pinky's and Inky's famous *up*-direction overflow bugs are **not** reproduced, on the owner's instruction. Scatter targets are off-grid, so `playfield_is_walkable` cannot describe them — being off the grid is the property the test checks. A `difficulty_t` comparison that had been reading padding since it was written started failing once the new dot-limit fields moved the padding, and was fixed. Measured on the board: RAM 67.2 %, flash 15.8 %. **The route search is superseded by DEC-049 (M6) and deleted**; everything else in this row still stands. |

## 11.2 As-built vs. intended design

Where the current firmware differs from the target design in this doc set:

| Topic | Intended (spec) | As built (today) | Reconciled by |
|---|---|---|---|
| Init code generation | CubeMX-generated init/HAL ([§3.8](03-Architecture.md#38-build--toolchain), [D-003](05-Risks-Assumptions-and-Dependencies.md#53-dependencies)) | CubeMX-generated init + HAL — **matches the spec again** (M1 took a register-level detour, DEC-001; M2 pivoted back) | DEC-012 |
| Core clock | not specified in the doc set | **SYSCLK 160 MHz** (PLL1 from MSIS 48 MHz, `M=3 → 16 MHz × N=10, R=1`), 1 kHz SysTick — documented in [M2 Board Bring-Up §2](../Design/M2-Board-Bring-Up.md) | DEC-004 (superseded) / DEC-012 |
| Pub-sub broker | One broker instance for the game's events, plus values copied across calls ([§3.2](03-Architecture.md#32-message-broker)) — **re-baselined to what is built** | `Services/msg_broker` + `Services/active_object`, used by `game` → `score` | DEC-015 / DEC-027 |

Everything else in the firmware matches the design as written. The mikroBUS pin
map is now **HW-confirmed** and [R-001](05-Risks-Assumptions-and-Dependencies.md#51-risks)
is closed (DEC-008), but only for the shield that has since been removed. The equivalent question for the X-NUCLEO-GFX01M2 was tracked as R-009 and is **also closed**: both halves of its pin map are measured, the display by `display_id` and the joystick by `joystick`, with the two checked against each other by `joystick_dot` ([M2 Board Bring-Up §1](../Design/M2-Board-Bring-Up.md)).

([A-004](05-Risks-Assumptions-and-Dependencies.md#52-assumptions)) and the host/SDL
platform-port interfaces ([§3.8](03-Architecture.md#38-build--toolchain)) — remain
tracked in their respective docs and are not repeated here.
