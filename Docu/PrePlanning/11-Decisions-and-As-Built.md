# 11 Decisions & As-Built

[← Back to Index](Index.md)

This document records **implementation decisions actually taken** and where the
built firmware **deviates from the intended design** described elsewhere in this
set. It exists so a reader starting from zero can tell what is true *today* (as
built) from what is *planned*. Requirements ([02](02-Requirements.md)) state the
target; this log states the current reality and the reasoning.

Decisions carry a `DEC-xxx` ID. When a decision is superseded, mark it and add a
new row rather than editing history.

| DEC-012 | **Pivot back to STM32CubeMX + STM32 HAL** for the M2 board bring-up (supersedes DEC-001/DEC-009). Pin/peripheral config is owned in the CubeMX `.ioc`; the export lives entirely under `Firmware/ThirdParty/STM32_G431RB_HAL/` (its own `Core/`, HAL+CMSIS, linker, and a `cmake/stm32cubemx` interface lib). | DEC-013 | **Post-M2 structural refactor from the owner's review** (PR #6; partially supersedes DEC-009's naming). Five things changed. (1) **BSP naming unified on the `_bsp` suffix** — `bsp_i2c`→`i2c_bsp`, `bsp_spi`→`spi_bsp`, `uart`→`uart_bsp`, `systick`→`systick_bsp` — which also retires the DEC-012 extern-handle workaround, since the modules no longer clash with CubeMX's generated `i2c.h`/`spi.h` and include them directly. (2) **New `Bsp/dio_bsp`**, modelled on the reference project's `dio_bsp` (`set_pin`/`get_pin`, plus `toggle_pin` for the display's EXTCOMIN): pins are named through `dio_bsp_pin_e` and it is the **only** module permitted to call HAL GPIO. (3) **`Bsp/button` replaced by `Bsp/switch` + `Bsp/user_button`** — a reusable debounced-input primitive and this board's B1/PC13 instance — sampled at a steady 1 ms from a tick hook rather than at main-loop speed. (4) **`millis()`/`delay_ms()` removed from the tick module** in favour of `Services/delay` (the one blocking wait) and `Services/sw_timer` (all timeouts and periodic work, ported from the reference project); no tick arithmetic remains in the firmware. (5) **`retain_ram` reduced to the reference API** (`retained_ram_write`/`read` over a byte buffer) with the `ott_spec` layout moved into `Test/Target/ott.c`, so the memory module no longer knows the data format. Alongside these, the [c-code-style](https://github.com/MaxLell/c-code-style) standard was applied across every file (Allman braces, `in_`/`out_` pointer prefixes, named constants, no abbreviations, `ASSERT` preconditions) with the config vendored as `Firmware/.clang-format`; the `lacheck`/`dispdiag` diagnostics were deleted now that R-001 is closed; and the cross-toolchain moved into `CMakeLists.txt` above `project()`, removing `Firmware/cmake/`. | post-M2 | Convergence with the reference firmware so modules are recognisable across both repos, and one owner per hardware-access path (GPIO, timing) instead of several. | Layout rules updated in [§3.9](03-Architecture.md#39-firmware-source-tree-layout). The 1 ms hook is a strong override of the HAL's `__weak HAL_IncTick()`, chosen so the generated `stm32g4xx_it.c` needs no edit and a CubeMX regen cannot drop it. The `button` OTT became `user_button`. |

| DEC-014 | **Message broker built as specified in [§3.2](03-Architecture.md#32-message-broker).** Instance-based (`self` first, all state inside), subscribers register an **output queue** rather than a callback, fixed-size messages copied by value, per-subscriber drop counters for slow-consumer isolation, and a `has_input_space` backpressure check (NFR-105). Split into four modules: `Services/msg` (the vocabulary of [§3.3](03-Architecture.md#33-message-definitions), header-only), `Services/circular_buffer` (a generic element-agnostic ring buffer, caller-supplied storage, no heap), `Services/msg_queue` (a `msg_t`-typed skin over it) and `Services/msg_broker`. Names follow §3.2.1's sketch — `msg_*`, `msg_t`, `msg_id_e` — and the topic IDs match §3.3's table verbatim (`MSG_INPUT_DIRECTION`, ...). | M3 | Everything communicates through the broker (FR-103), so its types appear in every module. `msg` is the one abbreviation the owner explicitly wants kept short (PR #8 review), which narrows the no-abbreviation rule of review note 1.1.2 rather than replacing it. The ring buffer is separate because the arithmetic is identical whatever is queued and is where wrap-around bugs live. | FR-108 wants a worker task per broker; FreeRTOS is M4, so `msg_broker_process()` is the worker body called from the super-loop, with no API change when the task arrives. **(Threading superseded by DEC-027: there is no task, and the owning loop names its own fan-out point.)** Unlike the singleton it was adapted from, `msg_broker_init()` does **not** assert "not already initialized" — on an instance that reads uninitialized memory. 102 host unit tests; not yet wired into `app_main`, so it enters the binary with the first module that uses it. |
| DEC-015 | **Active-Object base built as the reusable template of [§3.5](03-Architecture.md#35-software-module-template-active-object)** (FR-109), in `Services/active_object`. An object owns its **single inbound queue** (a `msg_subscriber_t`), a dispatch handler, and an opaque `context` pointer to the module's private state — so a module contributes only its handler and its data, and the state is reachable only while that handler runs. Subscribing takes the broker explicitly, because a module may sit on the system broker or on the game's internal one (FR-110, §3.6). Two of the pattern's rules are **enforced rather than documented**: run-to-completion asserts on re-entry (a handler that dispatches back into its own object is caught instead of mutating state mid-update), and asynchronous-only follows from the broker's output queue, which a unit test pins down by showing a handler's publish is not delivered until the broker runs again. | M3 | §3.5 asks for the boilerplate to be factored out; §3.6 alone puts seven more modules on this base, so its invariants are worth checking once here rather than per module. | Polling `active_object_process_all()` is the **host** model, not a stand-in for tasks: §3.4 says the host build runs these "as plain functions/loops driven by the SDL event loop instead of tasks". Under FreeRTOS (M4, DEC-002) the task body becomes the same call in a loop and no module changes. **(Superseded by DEC-027: no RTOS arrives, and `score` is the one module on the template rather than every module.)** **No FSM helper yet** — §3.5 mentions a state machine, but the reference project keeps `fsm` as a separate module; it gets added when a module actually needs states. 115 host unit tests. |

| DEC-016 | **No message carries a pointer; the render path is three modules and two messages.** The [R-007](05-Risks-Assumptions-and-Dependencies.md#51-risks) exception — a handle to a double-buffered snapshot — is withdrawn. **Game** publishes `MSG_GAME_STATE`, one coherent state per simulation step (56 bytes: two 99-bit pellet maps, five actors with their between-cell progress, and a few counters). **Game-View** holds it, runs at the *frame* rate rather than the step rate, interpolates ([10 §10.1](10-Pacman-Game-Design.md)) and publishes `MSG_DISPLAY_LIST` — what should be on screen now, in pixels. **Render** draws it and is the only module that decides **what changed**. Also settled: entities keep cell-granular *rules* and gain a sub-cell fraction that only the view reads. | M3 | R-007's premise was wrong. What is large is the rendered image, not the state, and the image never has to travel. Withdrawing the exception removes the second frame buffer with it — which was the harder problem, since one is 60 % of SRAM and two do not fit. Interpolation is what makes the 60 FPS of NFR-002 worth having: cell-granular drawing is a 21-pixel jump 6.7 times a second, which [M2 §3.2](../Design/M2-Board-Bring-Up.md) measured as visibly choppy no matter what the panel does. | Render owns the delta because it is the only module that knows what it drew *and* what it costs — 2.08 ms for two small rectangles against 252 ms for a full frame. `MSG_PAYLOAD_MAX_SIZE` grows from 16 to 64 bytes and `msg.h` stops including `framebuffer.h`, so the message vocabulary no longer depends on the image format at all. |
| DEC-017 | **One maze for every level; the difficulty is the arcade's own, in a module of its own.** FR-025's five distinct mazes are withdrawn. The playfield is a single 28 × 31 layout ([10 §10.2](10-Pacman-Game-Design.md)) — the size FR-022 always asked for, and only now affordable, since 28 columns of 8 px need a panel wider than the 128 px this project started on. What makes level 15 harder than level 1 is instead the progression of [§10.9](10-Pacman-Game-Design.md), transcribed from the arcade: per-level speeds for Pacman and the ghosts, a ghost that crawls in the tunnel, a Pacman who is slower while chewing, a shrinking frightened window with a flashing warning, per-level scatter/chase plans, and **Cruise Elroy** — Blinky accelerating in two stages as the maze empties, and no longer going home during scatter. It lives in `App/difficulty`, a stateless lookup holding the table in the arcade's own units (percentages of full speed, dot counts, seconds) and handing out milliseconds. FR-027's finish line moves from level 5 to **level 21**. | M3 | Five hand-authored mazes were a way of making levels differ, invented because the difficulty model was thin. The arcade's answer is better and is already designed: it is the difference between "the walls moved" and "Blinky is behind you and there are nine pellets left". Keeping the table in percentages is what lets the transcription be reviewed line by line against its source, which for twenty-one rows of hand-typed numbers is the only real defence. 21 is where the arcade's table stops changing, so it is the honest place to end a run. | Each ghost needs its own movement accumulator, since Elroy and the tunnel mean no two of them share a speed. The Elroy thresholds are absolute pellet counts and transfer unmodified only because this maze holds 243 pellets against the arcade's 244; `playfield_get_total_pellet_count()` and a unit test exist so a redraw cannot break that quietly. Tunnel cells are marked in the map rather than derived from the tunnel's row — the junction the tunnel opens onto is not tunnel. `MSG_PAYLOAD_MAX_SIZE` grows to 256 bytes, because the state's two pellet maps are now 868 bits each; the argument that withdrew [R-007](05-Risks-Assumptions-and-Dependencies.md#51-risks) still holds, with three orders of magnitude of margin instead of four. `playfield_load_level(pf, level)` becomes `playfield_load(pf)`. |

| DEC-018 | **Interpolation measures the step already taken, and the sprites are the arcade's own.** Two fixes that both came out of playing it. (1) `cell_progress_t` changes meaning from "how far towards the next cell" to **"how far into this cell from the last one"**, and Game-View draws backwards from the cell instead of forwards along the facing. An entity that did not move reports *arrived* rather than a fraction. (2) The hand-drawn art in `sprite_set` is replaced by the **1980 sprite and tile ROM**, decoded offline: Pacman's three-frame chew per direction, the ghosts' two-frame skirt per direction, the frightened pair, and the two pellet tiles. West and north Pacman are the cabinet's hardware mirrors of east and south, with its position offset folded into the data and a unit test checking the mirrors against their originals. | M3 | (1) was a real bug with a clear cause: the old scheme interpolated towards a cell that is only chosen when the next step happens, so at a corner it either slid a cell the wrong way and snapped, or — facing a wall — stood still for a period and then jumped. Both are the same mistake, extrapolating along a guess. Measuring the step that has already happened needs no guess. (2) the hand-drawn figures were placeholders and looked it; the originals are a fixed, checkable reference and cost nothing at run time. | The frame at a step boundary is now identical either side of a turn, which is what a unit test asserts rather than an eye. A dot is eaten the moment the model enters the cell, so it now vanishes as Pacman's leading edge reaches it rather than as his centre does — half a sprite earlier than the arcade, and the price of not guessing. Pacman's chew and the ghosts' skirt are clocked by the step rather than by a frame counter, so a ghost slowed by the tunnel visibly waves more slowly. The sprite data is Namco's: fine for a private build, not for anything distributed. |

| DEC-019 | **The maze is transcribed, not authored, and it is written down twice.** The walls are drawn with the arcade's own line and corner tiles — thin blue outlines and a pink gate instead of filled blocks — which forced the layout itself: a tile map only fits the maze it was drawn for, and the hand-drawn 28 × 31 one was wrong in 94 of its 868 cells. Both now come from the same source. `playfield` keeps the **rules** map (wall, pellet, pen, tunnel) and `game_view` keeps the **appearance** map, one arcade tile letter per cell, with `sprite_set` holding what each letter draws. `game_view_is_wall_drawn_at()` exists so a unit test can check every cell of the two against each other. | M3 | Filled blocks were the last thing that still looked hand-made. Deriving the tiles from the wall bitmap instead would have meant inventing corner art — the very thing the owner had just rejected for the sprites. Keeping the two maps apart is the MVC split doing its job: neither is derivable from the other, so one table cannot serve both, and a mechanical check is what makes the duplication safe rather than a trap. | The pellet count becomes **exactly the arcade's 244**, so §10.9's Cruise Elroy thresholds stop depending on the coincidence that the hand-drawn maze held 243. Pacman now starts in the corridor below the ghost house, walled above and below, and the house is three rows rather than two — both of which moved a good deal of test scaffolding. `game_view_t` loses its 5 kB `playfield` copy, which only the old wall lookup needed. The gate is drawn but passable: the arcade's one-way rule keeping Pacman out of the house is still not modelled. |

| DEC-020 | **The HUD is a fixed list of slots, and Render sends a tile as a tile.** The score, level and lives ([10 §10.10](10-Pacman-Game-Design.md)) are described as a fixed-length list whose content is a pure function of the state; asking the same question of the state last drawn gives what is on the panel, and only the difference is sent. `game_view_t` keeps a 20-byte `drawn_hud` for that. The alphabet is the arcade's own font, decoded from the tile ROM at its ASCII codes, so `sprite_set_get_glyph()` is arithmetic. Separately, `render_draw` was presenting **every** background item as `RENDER_SPRITE_MAX_SIZE` — 16 x 16 for an 8 x 8 tile — and now uses the sprite's own size. | M3 | The score moves on almost every pellet, so "redraw the HUD when something changed" had to mean the digit that moved rather than all seven; at 5 Mbit/s the difference is bigger than the five actors cost. The transfer bug was found by measuring the target footprint rather than by looking: it quadrupled every field transfer, which is invisible on a frame that changes one pellet and is a third of a second of black screen across the 868 tiles of a level change. | The level repaint drops from roughly 0.36 s to 0.1 s, and a test now asserts what size actually reaches the display port rather than only what lands in the frame buffer. Lives are drawn as the count the model holds, not the arcade's reserve men, so the panel cannot disagree with `game_get_lives()`. The whole A-Z is in flash for two words — 2 kB, and the menu and score screens (FR-001/002/023) are all text. Cost measured with arm-none-eabi-gcc: +2.5 kB flash, +20 B RAM. |

| DEC-021 | **One frame buffer, owned by Render, borrowed by the on-target tests.** `Test/Target/ott_framebuffer` and `App/render` had each allocated a 153,600-byte buffer, both headers stating that only one fits. `ott_framebuffer_get()` now forwards to `render_get_framebuffer()`, which is writable for the purpose, and `App/render` (with `sprite_set` and `Services/sprite`) joins the target build. The tests keep drawing with `gfx` and presenting with `display` — they do **not** draw through Render. | M4 prep | 153,600 bytes is 60 % of the contiguous SRAM; two of them are 300 kB against 256 kB and would not link. Nothing had noticed because the game is not in the target image yet, so this was the first thing standing in the way of wiring it. Routing the tests *through* Render was considered and rejected: `render_draw` takes a display list of sprites and these draw primitives, and `ott_display_test` measures `display_present` against `display_present_region` — which is precisely the decision Render takes over, so putting it in the path would remove the thing being measured. A bring-up test also has to fail in one place, and through Render a red result could be the driver, Render or `sprite_set`. | The dependency now runs `Test/Target` → `App/`, the wrong way for a test of a lower layer. Accepted knowingly: the alternative was a third module owning the buffer, and one forwarding call was the smaller price. `--gc-sections` keeps the cost at 8 bytes of flash, because only the accessor is reachable until the game itself is wired. A caller drawing straight into the buffer steps around save-under, which is harmless only because the OTT flow runs one scenario per reset ([09](09-OTT-Mechanism-and-Reset-Flow.md)) and the game is not running during it. |

| DEC-022 | **The game is normal operation; a test replaces it for one boot.** `app_main` starts the game at power-on and runs it in a loop that also polls the console. `ott <name>` still stores the request and resets, and `ott_execute_pending()` now returns whether it ran — on that boot the board stays on the console rather than starting the game, and `reset` brings the game back. Joystick directions are read as a *level* once per frame; the centre key starts the next run once one has ended. `App/render` was already in the target build (DEC-021) and the rest of the game joins it. | M3 | The owner asked for exactly this shape: the game starts regularly, the console stays available, and configuring a test reboots into it and interrupts the game. Scheduling already worked that way — what was missing was that the game and a test are *alternatives* for a boot, not a sequence: starting the game after a test would paint over the panel the test left behind, while the harness is still reading the verdict off the same line. | Wiring the game in broke `run_ott.py`, and the failure was worth the trouble of chasing: the UART receive register holds one character with no FIFO, and a loop that now spends milliseconds inside a frame drops most of a command line. `console_poll_receive()` samples it from the 1 ms tick into a ring buffer of the console's own — hand-rolled rather than `Services/circular_buffer`, because that one shares a `count` between producer and consumer and here the producer is an interrupt. Characters must still arrive more than a millisecond apart, which typing and the harness satisfy and pasting does not ([RF-016](../Refactoring-Backlog.md)). Measured on the board: RAM 169,968 B (64.8 %), flash 80,857 B (15.4 %). Verified on hardware: game runs, console answers 25 of 25 command lines during play, OTT suite green three runs in a row. |

| DEC-023 | **The ghosts, checked line by line against the Pac-Man Dossier.** Distance becomes the squared straight line rather than Manhattan; Pinky looks 4 cells ahead rather than 2, Inky's offset is 2 rather than 1, Clyde breaks off at 8 rather than 4. Forced reversals happen on chase↔scatter and on entering frightened, but no longer on leaving it. The ghost house and its gate are their own cell kinds: Pacman may never cross the gate and a ghost only on its way out or after being eaten. Ghosts start where the arcade puts them — Blinky outside, above the gate — and are released by the arcade's dot counters, global counter and idle timer. The scatter targets move to the unreachable dead space above and below the maze, and are re-assigned: **Blinky top-right, Pinky top-left, Inky bottom-right, Clyde bottom-left**. Seeking becomes a route search. | M3 | The owner asked for A\* and for a comparison against the Dossier; the comparison turned out to explain more than the request did. "The ghosts feel dim" was arithmetic, not intelligence: Manhattan distance makes a detour cost the same as going straight, so visibly worse directions reached the tie-break as equals and won on ordering alone. The house being an ordinary corridor is why they wandered back into their cage and why Pacman could follow. The scatter corners were swapped within each pair, sending all four to the opposite side of the maze. | The route search is breadth-first rather than heuristic, and that is a considered choice: Pinky and Inky aim at cells that usually cannot be reached at all, and no heuristic prunes a search for something that is not there. Where the target is reachable it returns A\*'s route; where it is not, the nearest reachable cell — which A\* has no answer for. Fleeing stays greedy. Pinky's and Inky's famous *up*-direction overflow bugs are **not** reproduced, on the owner's instruction. Scatter targets are off-grid, so `playfield_is_walkable` cannot describe them — being off the grid is the property the test checks. A `difficulty_t` comparison that had been reading padding since it was written started failing once the new dot-limit fields moved the padding, and was fixed. Measured on the board: RAM 67.2 %, flash 15.8 %. |

| DEC-024 | **One frame, three callers: `App/game_session`.** The `game_tick` → `game_view` → `render` → present sequence, paced by a one-shot `sw_timer` that re-arms itself, moves out of `app_main` into its own module. The target's `app_main`, the host application and the new `ott pacman` all call it; each keeps its own input reading and its own printing. | M3 | The on-target test had to start a run, and the frame it needs is the frame `app_main` already had. Copying it would have put three copies of the two traps in the loop — the timer that has to re-arm itself, and the level handover that spans several display lists — and both had already cost a debugging session once. Worse, a copy makes the end-to-end test an exercise of the copy. | Input stays out: a joystick, a keyboard, and a joystick plus a confirm button are three different devices, and the callers say different things about what they see. Single-instance, file-scope state rather than an object, because there is one panel and one frame buffer behind it (DEC-021) and a second session would have nowhere to draw. `test_game_session` pins the two traps, including the one-frame regression that showed a maze and then nothing. |

| DEC-025 | **The high scores live in one flash page the linker reserves, and the cache is taken out of the loop.** `FLASH` is shortened by one 8 KB page and the page beyond it becomes its own `NVM` region; `Bsp/flash_bsp` erases and programs exactly that page, with the instruction cache disabled around every operation and invalidated afterwards. Above it, `App/high_score` keeps three scores behind a magic word, a layout version and a CRC-32, and writes only when the table changes. A `highscore` console command shows them and `highscore reset` clears them (FR-009, [10 §10.11](10-Pacman-Game-Design.md)). | M3 | FR-009 needs a power cycle survived, and `Bsp/retain_ram` only survives a reset. Reserving the page by convention — "nothing will grow that far, we are at 16 %" — is the version of this that erases part of the program the first time a score is saved; letting the linker do it turns that into a link error. | The cache was not a precaution: the first run of `ott high_score` on the board wrote three scores, reported success, and read the table back empty, because the ICACHE sits in front of the flash and caches literal reads from it. The driver offers *replace* rather than *write*, since flash erases whole pages and can only clear bits — a partial write is not something this hardware does, and offering it would be a promise the caller finds out about on the second write. Storing costs about 1 ms to erase and 10 ms for three writes against a 16 ms frame, which is why a run is offered to the table once, when it ends. The host port is a file next to the executable, because the property being stood in for is surviving a power cycle and an array in a process that exits stands in for nothing. Verified on the board: written, hardware-reset, read back. |

| DEC-026 | **The game is a state of `App/shell`, not the thing the firmware does.** Loading, menu, game, score, menu again (FR-001/002/003/023), with the two word screens drawn as ordinary background display lists through Render. The title is the tile ROM's font and the row under it is the arcade's own cast; there is no logo bitmap to decode. A `start` console command presses the start key, so the flow is drivable without a finger at the board. | M3 | Without it a run had no end: the board played, died, and sat there. The high-score table also needs a moment that is neither a frame nor a boot to be written in, and "the run just ended" is that moment. | The title reads `PACMAN`, not `PAC-MAN` — the decoded font is digits, letters and a space, and drawing a hyphen would be the invention avoided everywhere else. Two crashes came out of this and both were the same shape, an *init* being called again when a screen or a run starts: `render_init` handed `display_init` a second call, and `game_session_init` handed `sw_timer_create` a second registration. Both now bring their once-only part up once. Neither was reachable in the unit tests, because those mock the BSP boundary the assertions live below — an argument for the on-target tests, not against the unit ones. `test_shell` now fails on *any* assertion firing, which is what would have caught the missing hyphen: the probe otherwise records and returns, so a screen drawn with a character the font lacks passed on the host and spun in `while (1)` on the board. |


| DEC-027 | **No RTOS, and the requirements say so.** FreeRTOS is not introduced in M4 or later: CON-104 is withdrawn, FR-105 becomes *cooperative execution* — one loop plus the 1 kHz tick ([§3.4](03-Architecture.md#34-execution-model)) — and FR-108 keeps the broker's fan-out but drops the task that was to perform it. VT-INT-009 (the task-startup test) goes with them. CON-104 and VT-INT-009 are **deleted outright** rather than left as tombstones — asked for in review on PR #27: a retired ID that still names the thing keeps it alive in the reader's head, and this log is where the record belongs. Neither ID is reused. In the same pass FR-103 stops asking for *no direct cross-module calls* and asks instead for what the firmware actually guarantees: no shared mutable state, everything crossing a boundary a fixed-size value copied by value. The system-level broker of [§3.2.2](03-Architecture.md#322-firmware-structure-layered-calls-message-types-by-value) is not built and is not planned; the one broker instance that exists carries the game's events to `Score` (FR-110). | M3 | Asked for by the owner, and the game had already answered the question the RTOS was there to settle. The M3 firmware plays at 60 fps with the console answering between frames, on a loop nothing in it ever blocks — no waiting I/O, no device that replies later, no work that must proceed while another part is stalled. A scheduler's one real purchase is that a slow module cannot delay a fast one, and the frame budget bought that instead by being measured: five actors are 5.26 ms of 16.7 ms. Bringing tasks in now would add stacks, a port, priorities and races to a system that has none, in exchange for nothing observable. The FR-103 wording went the same way for the same reason — it described a bus that was never built, and a requirement no build satisfies is worse than none. | Documentation only: no code changed, and none needed to. What the docs lose is the claim that a queue sits between every pair of modules; what they gain is that the *reason* for a queue is written down (announcing something to an unknown number of listeners), so the next module that needs one has a test to apply rather than a rule to follow. The retired IDs are gone from the spec and recorded only here. `Services/msg_broker` and `Services/active_object` remain as they are: one user each today, and the pattern is what `Score` is built on. |
| DEC-028 | **Development is finished.** The project is closed as of 2026-08-04: no further milestone, no further refactoring, no further feature. The [Refactoring Backlog](../Refactoring-Backlog.md) is closed with every `RF-xxx` marked for what it is — obsolete, overtaken by later work, or never done — and nothing in it will be picked up. [§4.2](04-Implementation-Phases-and-Milestones.md#42-close-out) is the close-out record. | M3 | Asked for by the owner. The game is complete and plays on the board, both goals of the project are answered — a standalone arcade Pacman on the U545RE, and the question of how far an agent carries a disciplined embedded project — and the work that remained was polish on warts the project had already judged and written down. | **Two things this does not fix, and the record should say so plainly.** **NFR-003 ends unmet:** the input path is ~34 ms against its 30 ms budget, 32 ms of that the shared debounce window ([RF-014](../Refactoring-Backlog.md#rf-014)); the overshoot is a chosen deferral, not a discovered defect, and no player reported lag — but the requirement as written is not satisfied and closing the project does not satisfy it. **Two catalogued tests were never built:** VT-INT-013's automatic latency measurement (which is why the number above is M2's, taken against `joystick_dot` rather than the finished game loop) and VT-INT-016's scripted frame-rate assertion (the margin is known to be large from VT-INT-021's 175 fps ceiling, just not asserted by a script). Everything else in the catalogue passes, 357 host unit tests pass, and both builds are warning-free. |
| DEC-029 | **Development is reopened, and the maze is generated.** The project was closed on 2026-08-04 (DEC-028); the owner reopened it the same day to ask for randomly generated mazes instead of the one fixed layout. FR-029 is added, FR-025 stops saying every level plays the same maze, and `App/maze_gen` is a **port of the tetris-stacking generator from [shaunlebron/pacman-mazegen](https://github.com/shaunlebron/pacman-mazegen)** — the solution that repository's own README rates best of the four it tried. The port is deliberately faithful rather than tidied: the same decisions in the same order, drawing the same random numbers, including three places where the original relies on a JavaScript accident. | M4 | Asked for by the owner. Writing a generator from scratch would have meant inventing the aesthetic heuristics that make a maze read as Pacman's — no straight run of three, one long piece per maze, one row stretched and one column narrowed — which is exactly the research that repository already did and published. Porting it faithfully also made it **verifiable in a way an original could not be**: the original and the port were run against the same seeded PRNG and their output compared byte for byte over 300 seeds. Tidying the accidents would have produced a different generator with nothing to compare against. | The maze is 28 x 31 because the generator's 9 x 5 grid upscaled by three and mirrored *is* 28 x 31 — the same reason the arcade's is. The ghost house, its gate, the four ghost starts and Pacman's start are stamped at the arcade's own coordinates, which the generator's own grid already puts them at (checked over 2000 seeds), so ghost release, revival, the gate rule and the scatter targets keep the meaning they were verified with. **The tunnels are shorter than the arcade's** — one or two cells rather than six — because a generated maze has no room for the side masses; the tunnel is still a way round and still slows a ghost, but it is a weaker escape. The arcade layout stays in `playfield.c` as the reference and the unit-test fixture. Seeded from the tick at the moment start is pressed; `ott pacman` prints its seed so a maze can be reproduced. Retries are capped at 256 with an assertion rather than looping unbounded on a target. Details in [M4 Random Mazes](../Design/M4-Random-Mazes.md). |
| DEC-030 | **The maze's appearance is derived from its walls, not written down beside them.** `game_view`'s hand-transcribed tile map is gone. A wall cell on the panel edge carries the boundary line; any other carries part of its block's inset outline, chosen from which neighbours are open and, failing that, which diagonal is; the ghost-house box is stamped. Two tiles were added as **vertical mirrors of the top tees** — the 1980 ROM has no bottom-edge tee, because nothing is ever attached to the arcade maze's bottom wall. | M4 | Forced by DEC-029: there is no maze to hand-draw a tile map for. It also retires the duplication DEC-018 introduced — the maze was written down twice with a unit test holding the two together, which was the right answer while both were authored and is not once one is generated. 62 % of generated mazes attach a block to the bottom wall, so the two missing tiles are not hypothetical. | **Checked against the arcade's own hand-drawn map, which is now a test fixture in `test_game_view.c`: 764 of 764 cells outside the two tunnel masses match exactly**, concave corners and tees included. The 64 cells inside the masses do not, and the test asserts it is exactly 64 so the exclusion cannot grow quietly — there the arcade draws a six-cell-thick mass with the boundary family, a shape no generated maze has. Costs 868 bytes in `game_view_t` for the derived tile per cell, computed once per level. The per-frame cost is unchanged, measured by running the same `ott pacman` against `main` and against the branch: 8 ms of a 16 ms budget both times. |
| DEC-031 | **The outer frame is six pixels thick, not the arcade's two.** The panel's boundary tiles — four edges, four corners, eight tees — are widened to a 6-pixel band with a 1-pixel margin either side, which is the weight a two-cell wall inside the maze already renders at. The ghost house keeps the arcade's 2-pixel wall and gets four tiles of its own for it; it used to share the frame's. The 16 widened tiles are **generated** from the geometry rather than drawn by hand, so they are exactly symmetric. | M5 | Asked for by the owner, looking at the panel: the frame read as a thin line against walls three times its weight, because that is what it was — 2 px against 6. **It is a deliberate departure from the ROM**, and the reason the ROM is that way is geometric: the frame is one cell (8 px) thick where an inner wall is two (16 px), so 2 px is what leaves room for a corner radius. At 6 px there is no room, and the four screen corners become solid right angles. The owner was shown that consequence and chose the thickness anyway. | The alternatives were put and declined: a hollow double line (two 2-px lines, same 6-px span, corners stay curved) and 3 px flush to the edge (no new art at all, but still visibly thinner). Nothing else changed: the derivation picks the same tile *ids* it always did, so the appearance test still reproduces the arcade's own map for 764 of 764 cells — only those tiles' pixels are ours now. The tunnel mouths took a third attempt as a result: a 3-pixel block cap against a 6-pixel band left a visible step, so the band now simply stops square at the cell boundary. Flash +136 B. |
| DEC-032 | **A wall's outline is a 6-pixel stroke set 5 pixels in, whatever the wall's thickness; and a tunnel mouth is as wide as a corridor's own gap.** Two things the owner asked for after looking at the panel. The stroke: a wall two cells thick already rendered at 6 px, because its two 3-pixel tiles meet — a wall three or more cells thick showed only 3 px, because they do not. The outline is now drawn across **two** cell rings: the same rule run one cell further in, turned through half a turn, so the inner tile completes the stroke the outer one started. Where a wall is exactly three cells thick the two strokes leave 2 pixels between them and the middle is drawn **solid** instead. The mouth: the frame band now stops **5 pixels short** of the opening either side, making it 5 + 8 + 5 = 18 px — the same clear black a corridor leaves between two wall lines. | M5 | Asked for by the owner: the boxes' lines read as thin against the 6-pixel frame of [DEC-031], and the mouth read as a notch rather than an opening. Both were **measured before being changed** rather than judged by eye — 3 px against 6, and 8 px against 18. | **No new art for the stroke**, which is the pleasing part: every one of the twelve block tiles is the half-turn of another, checked by flipping the bitmaps and matching, so the inner ring is drawn with the tiles that already existed. Three tiles were added: two for the frame either side of a mouth, and one solid for the cramped three-cell case. **Consequence, and it is visible:** a wall three cells thick no longer shows a hole, so most generated boxes are solid — at 5 px margins the arithmetic leaves 2 px and there is nothing to draw. Only walls four cells or thicker read as outlines now. The arcade maze changes in 10 cells, all of them inside walls; the appearance test counts them rather than asserting them away, and still holds the derivation to the arcade's own tile in every cell the arcade draws. Flash +776 B. |
| DEC-033 | **The maze's outer wall is given a second cell, in the panel's own margin, and is then an ordinary wall.** The frame family — four edges, four corners, eight tees, two tunnel-mouth tiles — and every rule that went with it are **deleted**. What draws the outer wall now is the same block rule as everything else, because with two cells it is the same thing. The ghost house, which has no margin to borrow, keeps a one-cell wall and wears the 6-pixel band centred in it. | M5 | Four complaints from the panel in one round — pellets not centred, the joins to the frame changing thickness, the tunnel mouths still gappy, the house too thin — and **all four were the same cause**: a one-cell frame cannot carry the stroke the rest of the maze carries. Every wall inside is two cells and draws a 6-pixel stroke set 5 pixels in, which needs 16 pixels to sit in; squeezed into 8 the stroke moves, and then the corridor beside it is narrower than every other corridor, its pellets sit off the middle, and nothing lines up at a join. Patching the four symptoms separately would have meant a dozen more tiles and more special cases; giving the wall its missing cell removed the special case entirely. | The border is 8 px of margin either side of a 224 px maze in a 240 px panel, plus the row above; the lives moved one row down to make room below. **Measured after: the worst pellet offset anywhere in the maze is 0.0 px** (it was 2), and a tunnel mouth is 18 px, the same clear black a corridor leaves. Net **-19 tiles and -80 lines**, and flash went *down* 272 B. The field handover grows from 868 cells to 990 — one more message, no measurable frame cost. What is lost is the last of the arcade comparison for the outer wall: the appearance test now skips those 114 cells and the 40 of the house, counting both. That comparison was already hollow there — it matched tile *ids* whose art had been replaced in [DEC-031] — and saying so is better than keeping the appearance of a check. |
| DEC-034 | **The maze is drawn as geometry, not as tiles.** `sprite_set`'s 24 maze tiles, the letter map that named them and the two functions that looked them up are **deleted**. `game_view` computes each wall cell's pixels from one rule: *a pixel is ink when its distance to the wall's nearest edge lies in `[inset, inset + 6)`, where the inset is half the wall's spare depth, capped at 5*. The pixels travel in the display list — `DISPLAY_ITEM_WALL` carries an 8-byte bitmap instead of a drawing's name. | M5 | The tile alphabet was decoded from the 1980 ROM and was right for as long as every wall was two cells thick, which is what its pieces were drawn for: a piece has its ink at a fixed place in its 8 pixels, so it composes correctly only at that thickness. Every other thickness needed a family of its own, and **every seam between two families was a visible fault** — four rounds of them were reported from the panel ([DEC-031] to [DEC-033]), each fixed by adding tiles or special cases. The owner asked for shaunlebron's approach instead and said the original tiles were not needed. Width and inset are arithmetic now, so they are the same everywhere by construction rather than by case analysis. | Flash went **down 1.2 kB**; frame cost unchanged at 8 ms of 16, and the achieved rate is 58–59 fps as before (the 1 ms tick makes ±1 fps of noise on that measurement). Two things are known departures. The **ghost house is told its depth** rather than measured: it is a ring one cell thick, and depth is found by running along an axis until the wall ends, which inside a ring never happens — so its corners would measure the length of their own arms. Fair to be told, since the house is furniture at coordinates the game already depends on. And a wall **exactly three cells thick** shows a 2-pixel hole rather than none, because that is what the arithmetic says; [DEC-032]'s solid tile is gone with the rest. **What this costs in verification is the whole arcade comparison** — there is no tile to compare. What replaces it is aimed at what was actually going wrong: the two properties a player noticed are now unit tests that rebuild the picture from the display list and measure it — every pellet within a pixel of its corridor's centre line, and a tunnel mouth exactly as wide as a corridor's own gap. |
| DEC-035 | **The waiting ghosts are drawn half a cell to the right of the cell they stand on.** Drawing only: the cell itself, and everything the rules read from it, is untouched. Clyde's starting cell also moves from 16 to 15, which is where the arcade has him. | M5 | Asked for by the owner: Pinky centred under the gate, the other two touching him. **The grid cannot express it.** A ghost is 16 pixels wide and sits on a cell, so its centre falls on a cell *centre*; the gate is two cells wide and the house eight, so both of their centres fall on a cell *boundary* — four pixels away, always. Two cells apart puts the three of them shoulder to shoulder, and that part is exact; the last four pixels have to be carried by something that is not a cell. | Measured after: the gate spans 112..127 and Pinky's body 113..126, both centred on 119.5, with Inky and Clyde exactly 16 pixels either side. The **cost is a four-pixel sideways step** as a ghost leaves the house, where the offset ends — the owner was shown that, and the two alternatives (drawing the gate four pixels left instead, or leaving the group four pixels off), and chose this one. Clyde at 16 had been a transcription slip in the arcade map rather than a choice: it left an 8-pixel gap between him and Pinky, which is what started this. |


## 11.2 As-built vs. intended design

Where the current firmware differs from the target design in this doc set:

| Topic | Intended (spec) | As built (today) | Reconciled by |
|---|---|---|---|
| Init code generation | CubeMX-generated init/HAL ([§3.8](03-Architecture.md#38-build--toolchain), [D-003](05-Risks-Assumptions-and-Dependencies.md#53-dependencies)) | CubeMX-generated init + HAL — **matches the spec again** (M1 took a register-level detour, DEC-001; M2 pivoted back) | DEC-012 |
| Core clock | not specified in the doc set | **SYSCLK 160 MHz** (PLL1 from MSIS 48 MHz, `M=3 → 16 MHz × N=10, R=1`), 1 kHz SysTick — documented in [M2 Board Bring-Up §2](../Design/M2-Board-Bring-Up.md) | DEC-004 (superseded) / DEC-012 |
| Pub-sub broker | One broker instance for the game's events, plus values copied across calls ([§3.2](03-Architecture.md#32-message-broker)) — **re-baselined to what is built** | `Services/msg_broker` + `Services/active_object`, used by `game` → `score` | DEC-015 / DEC-027 |

Everything else in the firmware matches the design as written. The mikroBUS pin
map is now **HW-confirmed** and [R-001](05-Risks-Assumptions-and-Dependencies.md#51-risks)
is closed (DEC-008), but only for the shield that has since been removed. The equivalent question for the X-NUCLEO-GFX01M2 was tracked as R-009 and is **also closed**: both halves of its pin map are measured, the display by `display_id` and the joystick by `joystick`, with the two checked against each other by `joystick_dot` ([M2 Board Bring-Up §1](../Design/M2-Board-Bring-Up.md)).
Items still deferred **by design** (not deviations) — the NVM high-score format
([A-004](05-Risks-Assumptions-and-Dependencies.md#52-assumptions)) and the host/SDL
platform-port interfaces ([§3.8](03-Architecture.md#38-build--toolchain)) — remain
tracked in their respective docs and are not repeated here.
